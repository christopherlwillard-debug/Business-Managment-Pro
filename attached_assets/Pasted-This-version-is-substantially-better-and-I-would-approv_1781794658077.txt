The one thing I'd change

I would not add job_subcontractor_id yet.

Your note already identifies the problem:

job_subcontractors
PK = (job_id, subcontractor_id)

Trying to partially design around a future surrogate key can create confusion.

For now I'd keep:

job_id
subcontractor_id

in sub_payment_records.

That's enough to uniquely identify:

Plumbing
James Willard
$200 payment

You can always add a surrogate ID later when you refactor job_subcontractors.

So I'd remove:

job_subcontractor_id INTEGER ...

from this task entirely.

I really like this part

The migration audit step:

SELECT ...
FROM expenses
WHERE subcontractor_id IS NOT NULL
  AND job_sub_hours_id IS NULL

before migrating.

That's exactly the kind of protection you want.

A lot of people would have written:

INSERT ...
SELECT ...
FROM expenses
WHERE category='Subcontractor'

and accidentally migrated legitimate vendor/sub invoices that were never payment records.

The tighter filter:

description LIKE '%— % Pay%'

is much safer.
