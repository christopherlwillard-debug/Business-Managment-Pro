Honestly? I think you're about 80% of the way to something that most software companies don't even have.

The next rules I'd add aren't about coding—they're about protecting BuildPro from itself as it grows.

These are the ones I think you'll thank yourself for in a year.

RULE 33 — No Breaking Changes Without Migration
If a table, API, calculation, or business rule changes:

1. Existing data must continue to work.
2. Existing APIs must continue to function or provide a migration path.
3. Existing UI must not silently break.
4. Data migrations must be documented.

Breaking changes require approval.
RULE 34 — Every Feature Must Have an Owner
Every feature belongs to exactly one module.

Examples:

Accounting owns:

• Expenses
• Owner Pay
• Taxes

Jobs owns:

• Job Cards
• Scheduling
• Photos

Website owns:

• Websites
• SEO
• Landing Pages

No feature may belong to multiple modules.

This prevents "Who owns this logic?"

RULE 35 — No Hidden Business Logic

This one will save you a TON.

Business rules must never be hidden inside UI components.

Business logic belongs in services or engines.

React components should display information—not decide accounting rules.
RULE 36 — One Naming Standard

You have already hit this.

Owner Pay

Owner Compensation

Owner Withdrawal

Owner Distribution

Those are five names for the same thing.

I'd require:

Every business concept has one official name.

Aliases may exist for display purposes only.

API

UI

Reports

AI

must reference the official terminology.

RULE 50 — Stop Building If the Architecture Changes

This is probably my favorite.

If, during implementation, the architecture changes from the approved plan...

STOP.

Return to Architecture Review.

Do not continue coding.

Explain why.

Get approval.

Resume only after approval.

This would have stopped:

"I accidentally created owner_distributions..."

before it ever happened.

The one thing I think you're still missing

BuildPro Core Principles

5. Extend Before Create

Those become the philosophy behind every rule. When two rules seem to conflict, the Core Principles tell the AI which direction to choose.

My favorite new rule

If I could add only one more, it would be:

RULE 50 — Stop Building When Assumptions Change

If new information discovered during implementation changes the understanding of the problem, stop implementation and return to the Architecture Review Gate.

Do not continue implementing a solution designed for a problem that no longer exists.

Re-evaluate the architecture before writing additional code.

That single rule would have prevented the owner_distributions detour entirely. The moment Replit discovered your existing Owner Pay ledger, it would have been required to stop, revisit the architecture, and ask whether extending the existing system was the better approach before writing any new code.
