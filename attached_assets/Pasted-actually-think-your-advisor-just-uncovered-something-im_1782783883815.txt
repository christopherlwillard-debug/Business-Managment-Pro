Good catch. There is one architectural implication of the safer two-phase approach that we need to account for.

If Migration A copies the existing mfh_models table into a new mfh_home_series table while leaving the original mfh_models table intact as a rollback path, then we cannot also create the new mfh_models table in the same migration because the table name already exists.

I think the cleanest approach is:

Migration A (non-destructive)

* Create mfh_home_series.
* Copy all existing Home Series data from the current mfh_models table into mfh_home_series.
* Keep the original mfh_models table untouched as the rollback copy.
* Add any new columns and foreign keys that can coexist safely.
* Do not create the new mfh_models table yet.
* Do not drop or rename any existing tables or columns.

Publish the application and verify everything works correctly.

Migration B (cleanup and finalization)

Once the application has been verified:

* Drop the old mfh_models table (which currently stores Home Series data).
* Create the new mfh_models table (the actual model layer beneath a Home Series).
* Update the remaining foreign keys to point to the new structure.
* Drop obsolete columns and tables (mfh_manufacturers, old manufacturer references, etc.).

This keeps a complete rollback path during the deployment and avoids the table-name collision.

If delaying creation of the new mfh_models table causes application issues, then we should reconsider the naming strategy. Another option would be to temporarily create the new model table under a different name (for example mfh_series_models or mfh_home_models) during Migration A, then rename it to mfh_models during Migration B after the legacy table has been removed.

The primary goal should be a migration that is:

* Non-destructive during Migration A
* Fully reversible until the application is verified
* Free of table-name collisions
* Safe for a live production database with real business data

I actually prefer the temporary table name approach (mfh_series_models or similar) over delaying the table entirely. It lets the new application structure exist immediately while still preserving the old mfh_models table for rollback. Then Migration B becomes mostly a cleanup and final rename. That’s generally the pattern used for zero- or low-downtime production schema migrations.
