Old "Record Owner Pay" wrote to your expenses table — so your owner pay was sitting in your books as a business expense. Even after we patched the profit calc to exclude it, it was still conceptually wrong: equity withdrawals aren't expenses, they don't belong in that ledger at all.

Owner Distributions writes to its own table, completely separate. It never touches expenses, never risks showing up in a future report or filter that queries expenses, and it won't confuse accounting if you ever connect bookkeeping software.

The practical difference you'd feel:

Old: "Record Owner Pay" → expense row appears in your expense list with category "Owner Compensation" — messy and confusing
New: distribution goes into its own ledger under the Pay Breakdown tab only — clean separation

A better development rule for BuildPro

I would add this to your development standards:

Architecture Rule

Before creating any new database table, API endpoint, ledger, workflow, or business object:

1. Search the existing application for equivalent functionality.

2. If a similar system already exists:
   - Extend it.
   - Refactor it.
   - Reuse it.

3. Do not create duplicate sources of truth unless there is a documented architectural reason.

4. Every financial concept must have exactly one authoritative source of truth.

Examples:

• Owner Pay → One ledger
• Expenses → One ledger
• Payroll → One ledger
• Inventory → One inventory system
• Bank Transactions → One transaction source

If a proposed solution duplicates an existing system, stop and explain why the existing system cannot be extended before creating anything new.
This is especially important for accounting

Accounting systems are built around a single source of truth.

You don't want:

expenses
owner_distributions
owner_pay
owner_draws

...all representing the same underlying concept in different places.

You want:

One Owner Pay ledger that every screen reads from.

That way:

The Job page,
The Accounting page,
Reports,
Tax calculations,

...all stay synchronized automatically.

So I don't think the lesson is "Replit broke the rules." It's that your project has reached the point where architectural consistency matters more than fixing the immediate bug. As BuildPro grows, adding parallel systems to solve isolated issues will create technical debt. Extending the existing system is almost always the better long-term approach when it already models the concept you're trying to represent.
