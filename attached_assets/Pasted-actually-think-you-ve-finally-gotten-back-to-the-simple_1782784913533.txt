I think we’ve over-engineered this.

We’re trying to preserve a very small amount of MFH setup data:

* ~10 Home Series
* 3 Construction Types
* 2 Pricing Guides
* Guide Items
* Guide Add-ons
* No production jobs currently depend on the MFH feature.

Instead of building permanent compatibility layers and complicated migrations, I’d rather treat this like a one-time data conversion.

Proposed approach

1. Take a production database snapshot (rollback point).
2. Export all existing MFH data:
    * Construction Types
    * Home Series (currently stored in mfh_models)
    * Pricing Guides
    * Guide Items
    * Guide Add-ons
3. Verify the export before deleting anything.
4. Remove the old MFH tables from production.
5. Publish the new application so Replit creates the new schema exactly as defined by the current code.
6. Import the exported data into the new schema, preserving IDs where appropriate.
7. Verify:
    * Home Series are present
    * Pricing Guides work
    * Guide Items map correctly
    * Construction Types match
    * Applying a Home Series still produces the correct estimate

Why I prefer this

The current deployment blocker exists because Replit’s schema validator is trying to infer a complex rename.

If the old MFH tables don’t exist, there is nothing to rename. The validator simply creates the new tables from the current schema.

That removes the need for:

* compatibility layers
* multi-phase migrations
* rename heuristics
* temporary schemas
* cleanup migrations

The result is a clean production schema that exactly matches development.

The only requirement is that we export and verify the existing MFH data before dropping the old tables, and preserve IDs during the import so guide relationships remain intact.

Before doing anything destructive, I’d like confirmation that this approach is safe with Replit’s deployment workflow.
