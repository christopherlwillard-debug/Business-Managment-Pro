Honestly, I think BuildPro has reached the point where you need engineering rules, not just coding tasks. Every hour you spend preventing bad architecture will save dozens of hours of cleanup later.

If I were creating the BuildPro Constitution, these would be my top rules.

1. Single Source of Truth (Highest Priority)

Every business concept has exactly one authoritative system.

Owner Pay → One ledger
Expenses → One ledger
Inventory → One inventory system
Payroll → One payroll system
Invoices → One invoice system
Mileage → One mileage system
Bank Transactions → One banking ledger
Customers → One customer record

Never duplicate a business concept.

Before creating:

API
React component
Page
Report
Ledger

If one exists:

Explain why it cannot be reused.
Ask before creating another.

The rule I think will save you the most time

If I had to pick just one additional rule, it would be this:

RULE 0 — NO NEW DATABASE TABLES WITHOUT ARCHITECTURAL REVIEW

Before creating any new table:

1. Search the entire project for similar functionality.
2. List all existing tables that overlap.
3. Explain why each cannot be extended.
4. Explain how the new table affects reports, accounting, payroll, inventory, and taxes.
5. Wait for approval before creating the table.

A new table is a last resort—not the default solution.

That single rule would have prevented the owner_distributions proposal, because the review would have discovered your existing Owner Pay ledger first. Over time, it will help keep BuildPro coherent, easier to maintain, and much less expensive to evolve.
