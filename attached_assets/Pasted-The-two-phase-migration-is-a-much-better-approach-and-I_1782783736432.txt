The two-phase migration is a much better approach, and I agree with the direction. However, before running this against production, I want to make two additional safety improvements.

1. Migration A should NOT rename the live mfh_models table.

Instead of renaming the existing table, Migration A should:

* Create the new mfh_home_series table.
* Copy all data from mfh_models into mfh_home_series.
* Verify that the copied row count matches the original.
* Leave the original mfh_models table completely intact.

Only Migration B should remove the old mfh_models table after the application has been published and verified working.

This gives us a real rollback path because the original production data still exists during the transition. If anything unexpected happens after publishing, we can simply point the application back to the original table without restoring the database.

2. Every structural operation should be completely idempotent.

Every operation should be protected so it can safely run multiple times without failing.

This includes:

* Table renames
* Column renames
* Table creation
* Column creation
* Constraint creation
* Constraint removal
* Sequence renames
* Table drops
* Column drops

Each step should be wrapped in IF EXISTS, IF NOT EXISTS, or equivalent conditional checks using information_schema or pg_catalog.

The migration should never assume an object exists. It should verify first, perform the action only if necessary, and safely skip work that has already been completed.

The overall goal

Migration A should:

* Create the new structure.
* Copy the data.
* Add the new foreign keys.
* Leave every existing production object intact.
* Perform no destructive operations.

After publishing, verify that:

* The application loads correctly.
* Existing jobs still work.
* Estimates still work.
* Pricing still works.
* The Home Series feature behaves correctly.
* No production data has been lost.

Only after the application has been confirmed working should Migration B run, which can safely:

* Drop obsolete foreign keys.
* Drop obsolete columns.
* Drop the old tables.

This approach provides the safest possible deployment for a live production database containing real business data. It preserves a rollback path, minimizes deployment risk, and prevents any destructive changes until the new application has been fully verified in production.
