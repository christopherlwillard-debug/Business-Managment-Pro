From what you've shown over the last few days, the pattern has been:

Replit forms a theory.
It writes a task.
It changes code.
The symptom changes, but the underlying issue often remains.

That's a debugging process problem, not a coding problem.

I think you need a different workflow

Instead of asking:

"Write a task to fix it."

You need to ask:

"Debug it until you can prove the exact line that's wrong."

For example:

Do not create a task.

Do not propose a solution.

Debug the existing implementation.

For this issue, I want evidence, not a theory.

Show me:

1. The database record.
2. The API response.
3. The calculation using that record.
4. The frontend component receiving that data.
5. The exact line where the expected value disappears or changes.

Do not modify any code until the exact failing line has been identified.

If you cannot identify the exact line, continue debugging instead of proposing another implementation.

That changes Replit's job from architect to debugger.

I think another rule belongs in your Constitution
RULE 28 — Debug Before Design

If an existing feature is not working:

Do not redesign it.

Do not create replacement tables.

Do not create replacement APIs.

Do not create replacement workflows.

First identify the exact point where the existing implementation fails.

Only after the root cause is proven may architectural changes be proposed.

Creating owner_distributions.
Proposing another gas expense workflow.
Adding duplicate financial logic.

Because the first step would always be:

"Show me where the current implementation breaks."

I also think Replit needs to stop using this phrase:

"Found the root cause."

Unless it can immediately prove it with:

The database row.
The API payload.
The frontend state.
The exact line of code.

Otherwise, it's really saying:

"Here's my current hypothesis."

Those are not the same thing.

So I think your instinct is right. Don't let it spend another hour writing tasks. Then I'd add another one.

RULE 29 — Evidence Before Conclusion

Do not state:

• "Found the root cause"
• "Fixed"
• "Resolved"

unless evidence is provided.

Evidence must include:

• Database record (if applicable)
• API response
• Calculation output
• Frontend state or rendered data
• Exact line of code responsible

If evidence cannot be provided, describe the finding as a hypothesis rather than a confirmed root cause.

And probably the biggest one...

RULE 30 — Do Not Solve Unknown Problems

When the cause of a bug is unknown:

Do not create implementation tasks.

Do not design replacement systems.

Do not create workaround features.

Continue debugging until the cause is known.

Tasks should only be created after the failing component has been identified.

I'd also change your Mandatory Architecture Review Gate into a broader Engineering Review Gate.

Every bug would begin with:

Engineering Review

□ Is this a bug or a new feature?

□ Does this already exist?

□ Has the current implementation been traced?

□ Has the failing line been identified?

□ Is the proposed fix based on evidence instead of assumptions?

□ Is a redesign actually necessary?

Only after these questions are answered may implementation begin.
