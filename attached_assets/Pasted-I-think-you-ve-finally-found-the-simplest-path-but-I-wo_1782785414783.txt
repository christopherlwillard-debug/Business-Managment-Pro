I think you’ve finally found the simplest path, but I would make one important correction before you tell Replit to proceed.

The statement:

“With no MFH tables in production, the validator generates only CREATE TABLE statements.”

has not actually been proven.

It’s a reasonable hypothesis, but nobody has demonstrated that Replit’s deployment validator behaves that way. The validator has already shown that it performs its own schema analysis and safety checks. It may still refuse to proceed if dropping those tables represents data loss, even if they are unrelated to the new schema.

So I would avoid presenting that as a fact.

Instead, I’d send something like this:

⸻

After stepping back, I think we’ve been trying to solve this in a much more complicated way than necessary.

The only production data we need to preserve is:

* Construction Types
* Home Series (currently stored in mfh_models)
* Pricing Guides
* Guide Items
* Guide Add-ons

There are currently no production jobs depending on the MFH feature.

Rather than maintaining complicated compatibility layers and rename migrations, I’d like to treat this as a one-time data migration.

Proposed workflow

1. Create a production database snapshot.
2. Export all existing MFH data.
3. Verify the export.
4. Remove the legacy MFH tables.
5. Publish the new application so the current schema is created.
6. Import the exported data into the new schema while preserving IDs.
7. Verify that Home Series, Pricing Guides, Guide Items, and Construction Types all match the original data.

Before proceeding

The one thing I’d like confirmed is this:

Will Replit’s deployment validator successfully create the new MFH schema if the legacy MFH tables have already been removed, or will it still block the deployment because it detects destructive schema changes?

If the validator allows that workflow, this is dramatically simpler than maintaining custom migration logic and compatibility layers.

If it does not, then the limitation is the deployment validator itself rather than our migration.

⸻

I would not tell them:

“The validator will generate CREATE TABLE statements and it works.”

because none of us has actually observed that behavior yet.

One more thing I noticed

You also said:

“No code changes required.”

I would be careful with that statement as well.

If your application now expects tables like mfh_home_series and the published code references them, then the schema must exist before that code starts serving requests. Whether that happens during deployment or before the new application starts is something Replit controls.

So I’d phrase it as:

“Assuming the deployment creates the new schema before the new application begins serving requests, no additional application code changes should be necessary.”

⸻

Overall, though, I think this direction is far more reasonable than the migration complexity you were headed toward. The remaining question is simply how Replit’s deployment system behaves, not how to write another elaborate migration.
