# Phase 5: Component Work Sessions

## Status

Architecture approved. Ready for implementation planning after spec review.

## Goal

Let authorized users record simple actual production work against a job and an
approved production component. A record identifies the work date, worker, and
actual hours without becoming a time clock, payroll entry, expense, presence
record, checklist update, or Knowledge Center input.

Phase 5 ends with operational history that can be read and corrected. It does
not add learning, forecasting, benchmarking, or financial reporting behavior.

## Decisions

- The source of truth is a new Jobs-owned operational table,
  `job_component_work_sessions`.
- `job_sub_hours` is not reused. It has payroll, expense, payment-status, and
  job-profit side effects.
- `job_labor_entries` is not extended. It is an existing crew-summary input
  used by Knowledge Center behavior and lacks a dated component-level fact
  model.
- `job_daily_presence` is not reused. Presence remains a job/day fact, not
  proof of work on a component.
- The existing `subcontractors` roster is the only assigned-worker entity in
  Phase 5. “Assigned worker/member” means an assigned subcontractor on the
  job; there is no separate member directory in this phase.
- Each record uses an assigned subcontractor when available, or a supplied
  worker name for someone outside the job roster.
- Each record stores hours only. There are no start/end timestamps, clock-in
  states, breaks, approvals, rates, amounts, or pay status.
- The record references the exact `job_production_components` snapshot used at
  creation. Expected component fields remain owned by that snapshot and are
  never copied into work-session calculations.
- Existing component snapshots remain versioned. A later snapshot revision does
  not rewrite historical work-session rows.
- The schema lives in `lib/db/src/schema/job-component-work-sessions.ts` and
  is exported from `lib/db/src/schema/index.ts`. The SQL migration belongs in
  `lib/db/src/migrations`; use the next migration generated by the existing
  database workflow rather than adding a runtime migration endpoint.

## Data model

Create `job_component_work_sessions` with:

- `id`: serial primary key
- `job_id`: required foreign key to `jobs.id`, cascading with the job
- `production_component_id`: required foreign key to
  `job_production_components.id`, restricted from direct snapshot deletion
- `work_date`: required PostgreSQL date
- `linked_subcontractor_id`: nullable foreign key to `subcontractors.id`,
  set null if the roster record is removed
- `worker_name`: required trimmed display-name snapshot
- `actual_hours`: required `numeric(6, 2)` value with two decimal places
- `notes`: nullable trimmed text
- `created_at` and `updated_at`

The job is the authoritative ownership boundary. The API must resolve the
canonical business for the job and verify that the component belongs to the
same job before every read or mutation. Canonical business resolution uses the
job's `businessId`, falling back to its legacy `businessLine` slug lookup.
If neither resolves to a known business, every work-session operation returns
the existing `404 Job not found` boundary; Phase 5 does not claim or backfill
an unowned job. Existing legacy component snapshots with `businessId = NULL`
are treated as job-owned; they are not guessed, backfilled, or rejected solely
for being legacy rows. A non-null component business that conflicts with the
job's canonical business is rejected. The work-session table does not add a
second business ownership source that can drift from the job.

Validation:

- `work_date` must be a valid `YYYY-MM-DD` date.
- `actual_hours` must be greater than zero and no more than 24 hours per row.
- Values with more than two decimal places are rejected with `400`; they are
  never silently rounded by the database.
- `worker_name` is required whether or not a roster worker is linked.
- A linked worker must be an assigned subcontractor for the job.
- When a linked worker is selected, the server resolves and stores that
  subcontractor's current display name in `worker_name`; the client cannot
  use a different name for a linked worker.
- When `linked_subcontractor_id` is null, the caller must supply a non-empty
  `worker_name` for the outside worker.
- `worker_name` is limited to 160 characters after trimming. `notes` is
  limited to 2,000 characters after trimming; an empty trimmed note is stored
  as `null`.
- New rows may target only a persisted component with an `id` returned by the
  shared Phase 4 `getJobProductionComponents` path, where the component is
  current (`supersededAt = null`) and not `not_applicable`. The route must use
  that shared eligibility result rather than reimplementing a looser
  component-key check.
- If legacy data exposes more than one eligible current snapshot for the same
  `componentInstanceKey`, the mutation is rejected with `409` until the
  component snapshot history is repaired; Phase 5 does not guess which
  expected snapshot owns new work.
- Existing rows keep their component snapshot reference during edits; edits
  may change date, worker, hours, and notes but may not move work to another
  component. PATCH may add, change, or remove the linked worker. Removing a
  link from an assigned worker requires an outside-worker name; sending
  `linked_subcontractor_id: null` for an already-unlinked row may omit
  `worker_name` and preserve its existing outside-worker name. Adding or
  changing the link validates the new worker against the job roster and
  refreshes `worker_name`.
- Multiple workers and multiple component rows may exist for the same job and
  date. There is intentionally no uniqueness constraint for that combination.
- Add database checks for the positive/max hours range and indexes for common
  job/date and component lookups.
- The database check enforces `actual_hours > 0` and `actual_hours <= 24`;
  indexes cover `(job_id, work_date)` and `production_component_id`.
- Production component snapshots are superseded, not deleted. The restricted
  foreign key is a database guard against losing historical sessions. Deleting
  the parent job still removes all job-owned records together.

Database numeric values are exact decimals, not floating-point values. The API
accepts `actualHours` as a decimal string matching
`^(?:0|[1-9]|1[0-9]|2[0-4])(?:\.[0-9]{1,2})?$` and then requires the numeric
value to be greater than zero. Thus `"8"`, `"8.5"`, and `"8.50"` are valid,
while `"08"`, `"8.500"`, and `"24.01"` are rejected. Valid values are
normalized to two fractional digits. The API returns `actualHours` and all
`totalsByComponent` values as two-decimal strings (for example, `"8.50"`).

## API contract

Add job-scoped endpoints to the existing Jobs route module:

- `GET /api/jobs/:id/component-work-sessions`
  - OpenAPI operation ID: `listJobComponentWorkSessions`.
  - Requires the existing `businessId` query parameter as the selected
    business context.
  - Returns `{ sessions, totalsByComponent }`. `sessions` contains the job's
    rows joined to their component snapshot and includes component key/label/
    variant, snapshot version, worker name, linked worker ID, work date,
    hours, notes, and timestamps.
  - `totalsByComponent` is a read-time sum keyed by stable
    `componentInstanceKey`; it is not persisted and is not a second source of
    truth.
  - Sorts deterministically by work date descending, then ID descending.
  - Historical sessions remain readable even when their component snapshot is
    superseded.
  - Each session includes its referenced snapshot version so a revised
    component label or expected context cannot make old work appear to belong
    to the new snapshot.
- `POST /api/jobs/:id/component-work-sessions`
  - OpenAPI operation ID: `createJobComponentWorkSession`.
  - Requires the existing `businessId` query parameter as the selected
    business context.
  - Accepts `productionComponentId`, `workDate`, `linkedSubcontractorId?`,
    `workerName?`, `actualHours`, and `notes?`. `workerName` is required only
    when no linked subcontractor is supplied.
  - Resolves and validates the job, business, component, and optional roster
    worker before inserting.
  - Required JSON properties are `productionComponentId`, `workDate`, and
    `actualHours`. `linkedSubcontractorId` is an optional JSON integer or
    `null`; `workerName` is conditionally required as described in Validation.
    `notes` is optional and nullable.
- `PATCH /api/jobs/:id/component-work-sessions/:sessionId`
  - OpenAPI operation ID: `updateJobComponentWorkSession`.
  - Requires the existing `businessId` query parameter as the selected
    business context.
  - Allows correction of date, worker identity, hours, and notes.
  - Keeps `jobId` and `productionComponentId` immutable.
  - Is a true partial update: omitted fields remain unchanged; explicit
    `notes: null` clears notes; omitted `linkedSubcontractorId` leaves the link
    unchanged; `linkedSubcontractorId: null` removes the link and requires a
    non-empty `workerName`; a numeric linked ID changes the link and refreshes
    the server-resolved worker name.
  - `workerName` is accepted only when the resulting linked worker is null. It
    cannot override a linked subcontractor's name.
  - `workDate` and `actualHours` are optional fields but reject explicit
    `null`; `workerName: null` is rejected when the resulting linked worker is
    null. When the resulting linked worker is non-null, `workerName` must be
    omitted. When the resulting linked worker is null, an omitted
    `workerName` preserves the existing outside-worker name, while a supplied
    non-null string replaces it.
  - Supplying immutable `jobId` or `productionComponentId` fields in a PATCH
    body is rejected with `400`, rather than silently ignored. An empty PATCH
    body is also rejected with `400`.

Response conventions:

- `201` for successful create.
- `200` for successful list and update.
- `400` for malformed or invalid input.
- `404` for a missing or cross-business/cross-job job, component, worker, or
  session, using the existing job-not-found boundary where applicable.
- `409` for mutation attempts against a closed job.

There is no delete endpoint in Phase 5. This keeps recorded operational facts
historically available; corrections use PATCH. Hard deletion, voiding, and
audit-history treatment are deferred until a retention requirement exists.

Cross-business and cross-job access must return the existing job-not-found
boundary rather than revealing whether a session or component exists.

An absent or invalid business selector returns `400`; a valid selector that
does not own the job returns `404`. The selected business must agree with the
job's canonical business and the request cannot rely on the route's
all-business read fallback. Phase 5 accepts only the existing numeric
`businessId` selector for these endpoints; a `businessLine` request selector
without `businessId` is rejected. The job's legacy `businessLine` remains a
fallback only when resolving the job's stored canonical ownership.

Update the OpenAPI contract and generated client hooks/types in the same
change. The route handlers live in
`artifacts/api-server/src/routes/jobs.ts`, beside the existing job-scoped
production-component handlers. The API list endpoint is the only Phase 5
reporting/access path; there is no report or export consumer in this phase.
The read-time total is a small aggregation in that Jobs route response, not a
new calculation engine. Do not create a second route family for payroll or
labor.

Wire contract:

- Create and update request fields use camelCase.
- `productionComponentId`, `linkedSubcontractorId`, and `snapshotVersion` are
  JSON integers. Numeric strings for IDs are rejected.
- `actualHours` is a JSON string matching the decimal-string rule above.
- Nullable fields are explicitly marked below.
- `workDate` is a date-only string matching `YYYY-MM-DD`.
- `workerName` is a non-empty string when the final worker link is null.
- `notes` is either a trimmed string or `null`.
- A returned session has:
  `id: number`, `productionComponentId: number`,
  `componentInstanceKey: string`, `componentKey: string`,
  `componentLabel: string`, `variant: string | null`,
  `snapshotVersion: number`, `workerName: string`,
  `linkedSubcontractorId: number | null`, `workDate: string`,
  `actualHours: string`, `notes: string | null`,
  `createdAt: ISO-8601 timestamp string`, and
  `updatedAt: ISO-8601 timestamp string`.
- `totalsByComponent` maps every returned `componentInstanceKey` to a
  two-decimal hours string, including keys whose sessions belong to
  superseded or otherwise past snapshots.
- Validation and closed-job errors use `{ error: string }`, matching the
  existing Jobs API error envelope.

The contract source is `lib/api-spec/openapi.yaml`; generated API schemas and
methods are refreshed into
`lib/api-client-react/src/generated/api.schemas.ts` and
`lib/api-client-react/src/generated/api.ts` using the existing generation
workflow. Generated declaration output is not hand-edited.

Reads are allowed for any owned job, including completed, invoiced, and closed
jobs. Creates and PATCH corrections are allowed until the job is closed
(`status = "closed"` or `closedAt` is non-null); closed-job mutations return
`409`. This permits historical corrections on completed/invoiced jobs while
preserving the existing closed-job boundary.

The closed check and the session write occur in one transaction while holding
the job row lock. The existing close mutation is the status-writing branch of
`PUT /api/jobs/:id` in `artifacts/api-server/src/routes/jobs.ts`; it must use
the same row lock (or an equivalent conditional update) before writing
`status = "closed"` and `closedAt`. A close and a session mutation cannot both
claim to have occurred before the other. A job is treated as closed when either
`status = "closed"` or `closedAt` is non-null, including inconsistent legacy
rows.

The Phase 4 component snapshot/supersession path must acquire the same job row
lock before changing the current snapshot. A work-session mutation acquires
the job lock, re-runs `getJobProductionComponents`, and validates the selected
persisted snapshot after the lock is held. If supersession wins the race, the
mutation returns `409` and writes no session; if the work-session mutation
wins, the session references the validated snapshot that was current at that
linearization point.

## UI

Extend the existing production-component section in the Jobs detail surface.
Do not move this feature to Job Payroll or the Ready/Waiting planner queues.

For each current production component:

- Show a compact `Log work` action.
- Open a small form with:
  - work date, defaulting to today
  - assigned-worker picker plus an “other worker” name option
  - actual hours
  - optional notes
- Show the component's recorded work entries and a total actual-hours summary.
- Keep snapshot history separate from work-session history. Sessions are
  grouped under the current component's stable `componentInstanceKey` when
  that key still has a current eligible snapshot. “Current eligible” means
  the same current, non-superseded, non-`not_applicable` component set returned
  by the Phase 4 `getJobProductionComponents` path. Each session displays its
  own referenced snapshot version. If the current snapshot is
  `not_applicable`, superseded, or otherwise absent from that eligible set,
  show its entries in a separate “Past component work” section rather than
  hiding them. Past totals come from the same `totalsByComponent` map.
- Allow editing an existing entry from the same component section.
- Show loading, empty, validation, and mutation-error states explicitly.
- Invalidate only the work-session query after a successful mutation.
- The date picker defaults to the browser's local calendar date. The API
  stores and returns a date-only value without timezone conversion.

The UI implementation is the existing production-component block in
`artifacts/contractor-app/src/pages/Jobs.tsx`; no planner or payroll surface
is added.

Because this adds a new source-of-truth operational system, implementation
must also add its table/schema/API/UI/source-of-truth entry to
`.agents/architecture/SYSTEM_REGISTRY.md` through the approved architecture
change, and add the verified structural change to
`.agents/architecture/CHANGELOG.md`. The registry entry must state that the
table owns raw component work evidence only and has no payroll, financial, or
learning authority.

The form must be available only for the approved production components already
shown by Phase 4. Service, Finish Carpentry, standalone Drywall, Electrical,
HVAC, Inspection, Cleanup, and other excluded categories must not gain work
session controls through this feature.

## Explicit non-effects

Creating, editing, or listing a work session must not:

- insert, update, or delete `job_sub_hours`
- insert, update, or delete expenses or sub-payment records
- change payroll, rates, payment status, invoices, mileage, reimbursements,
  job profit, or financial reports
- create or update daily presence
- change job start dates, planning state, readiness, queue position, or
  checklist state
- write or update Knowledge Center records, accepted learning, benchmarks, or
  forecasts
- change production-component expected hours, duration, crew size, pricing,
  materials, or component status

The only derived value in Phase 5 is a read-time sum of raw actual hours for
display in the component section.

## Out of scope

- Time-clock behavior or start/end tracking
- Mobile-native application work
- Payroll or expense integration
- Production progress automation
- Component status automation
- Knowledge Center learning or forecast consumers
- New reports, exports, dashboards, or planner queue behavior
- Bulk import, bulk edit, or worker directory management
- Deletion or voiding of work-session history
