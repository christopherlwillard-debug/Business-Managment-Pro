**Rule 1 — Single Source of Truth**  
Status: **WARNING** — Severity: High

Two active code paths write to `expenses` with owner-pay and subcontractor-pay categories, partially violating ADR-001 and ADR-002:

1. **`record-owner-draw` endpoint** (`artifacts/api-server/src/routes/jobs.ts:2081`):  
   Still active. Inserts `category: "Owner Compensation"` into `expenses` when called from a job card. ADR-001 states `owner_capital_entries` is the sole owner pay ledger — this endpoint writes to `expenses` instead.  
   Tables: `expenses` (incorrect), `owner_capital_entries` (correct but unused by this route)  
   API: `POST /api/jobs/:id/record-owner-draw`

2. **Sub-hours auto-expense** (`artifacts/api-server/src/routes/job-sub-hours.ts:43–50`):  
   Auto-inserts `category: "Subcontractor"` into `expenses` when hourly sub time is logged. This is the documented sub-hours auto-expense pattern (memory: `sub-hours-auto-expense.md`) — sub hourly time creates a linked expense via `jobSubHoursId`. This is intentional, but it means `expenses` contains subcontractor payroll data, creating a dual-ledger situation with `sub_payment_records`. ADR-002 prohibits this but the pattern was grandfathered.  
   Tables: `expenses`, `sub_payment_records`  
   API: `POST /api/jobs/:id/sub-hours`

3. **`payments` table** (`lib/db/src/schema/payments.ts`):  
   An active `payments` table exists with a `subcontractorId` FK, used by `form-1099s.ts:41–46` to calculate 1099-eligible totals. This parallels `sub_payment_records` as a subcontractor pay ledger. Its relationship to `sub_payment_records` is undocumented in `DECISIONS.md` and not in `SYSTEM_REGISTRY.md`.  
   Tables: `payments`, `sub_payment_records`  
   API: `GET /api/form-1099s`

**Rule 4 — One Calculation Engine**  
Status: **FAIL** — Severity: Critical

Net profit is independently calculated in at least **5 separate locations**, each re-implementing the formula:

| Location | Formula | Surfaces |
|---|---|---|
| `jobs.ts:343–548` `GET /:id/profit` | `collected − jobExpenses − subLaborCost − allocPaid` | Job card P&L tab |
| `jobs.ts:604–726` `GET /profit-summary` | Same formula, batch version for multiple jobs | Job list summary |
| `jobs.ts:1203–1258` job listing | `revenue − materials − labor − otherOpex` | Jobs list page |
| `reports.ts:91–111, 175–215, 220–239, 1530–1654, 1677–1745` | Multiple independent profit formulas | Dashboard, P&L Report, Reserve |
| `lib/allocation.ts:20–88` | `afterWorkers × 0.95` (growth withheld) | Allocation/split calculations |
| `tax-reports.ts:343–394` | Schedule C gross profit/loss | Tax reports |

Rule 4 requires **one shared function** — this pattern produces calculation drift between surfaces.

**Rule 35 — No Hidden Business Logic**  
Status: **FAIL** — Severity: High

`artifacts/contractor-app/src/pages/Expenses.tsx` contains financial classification logic that drives accounting outcomes:

- `TRAVEL_CATEGORIES_LC` (line 101–112): Defines which expense categories are "travel" — this is a business rule about IRS classification
- `isTravelCategory()` (line 112): Returns the accounting classification of a category  
- Lines 3785–3786: `if (formJobId && isTravelCategory(val)) setCountsTowardJobProfit(false)` — **React component sets accounting ledger routing**
- Line 3800: Same logic on category change

`countsTowardJobProfit` is a database column that determines P&L routing. It is being set by a React component based on a frontend-defined business rule list. This is the root cause of the gas expense bug fixed in Aug 2026 and remains the pattern for all other travel categories.

## Summary

### 1. Duplicate Systems

| Concept | System A | System B | Risk |
|---|---|---|---|
| Revenue | `invoices` | `other_income` | Double-counting revenue possible |
| Sub Pay | `sub_payment_records` | `payments` | 1099 calculations use different table than payroll |
| Owner Pay | `owner_capital_entries` | `expenses` (via record-owner-draw) | Dual ledger for job-linked owner pay |
| Travel/Mileage | `mileage_logs` | `business_trips` | Undocumented overlap |

### 2. Duplicate Calculations

| Calculation | Locations |
|---|---|
| Job net profit | `jobs.ts:440`, `jobs.ts:716`, `jobs.ts:1258`, `reports.ts` (4+ locations), `allocation.ts:85` |
| Revenue (invoices + other income) | `reports.ts:91–111`, `reports.ts:175–215`, `reports.ts:220–239` |
| Growth reserve deduction | `allocation.ts:85`, `reports.ts:1467`, `reports.ts:1554`, `reports.ts:1738` |
| Meal deduction (50%) | `jobs.ts:415`, `tax-reports.ts:134`, `tax-reports.ts:202` |

### 3. Duplicate Tables

- `payments` and `sub_payment_records` — both track subcontractor pay for 1099/reporting
- `other_income` and `invoices` — both are revenue sources in reports

### 4. Duplicate APIs

- `GET /api/jobs/:id/profit` and `GET /api/jobs/profit-summary` — duplicate formula
- `reports.ts` income/expense sections independently re-implement the same job profit formula

### 5. Duplicate UI

- Owner pay shows up across `Accounting.tsx`, `Jobs.tsx`, `Dashboard.tsx`, `JobPayroll.tsx` with different terminology and different data sources in some surfaces

### 6. Architecture Debt

| Item | Debt Type |
|---|---|
| Growth % in `settings` table never read by calculations | Phantom configuration |
| `owner_capital_entries` schema missing FK that migration added | Schema-migration divergence |
| `record-owner-draw` writes to `expenses` (ADR-001 conflict) | Legacy route not removed |
| Job-sub-hours writes `Subcontractor` to `expenses` | Grandfathered dual-write pattern |
| 25+ tables not registered in `SYSTEM_REGISTRY.md` | Registry staleness |
| `SYSTEM_REGISTRY.md` describes IRS mileage rate as settings-based but `irs-rates.ts` hardcodes it | Documentation mismatch |

### 7. Highest Risk Areas

1. **Growth reserve calculation** — GROWTH_PCT=0.05 hardcoded in `allocation.ts` and `reports.ts` in 6+ places; the settings field `growthReservePct` has no effect on any actual calculation. Every payout and report is computed at the wrong rate if Willard ever changes his growth percentage in settings.

2. **Profit formula fragmentation** — 5+ independent implementations. A change to the profit formula (e.g., adding a new cost type) must be made in 5+ places simultaneously or surfaces diverge silently.

3. **Tax rates hardcoded** — SE tax, federal estimate, and Kentucky state rates are code constants. A rate change requires a code deploy to take effect, and Willard has no ability to update them without developer access.

4. **`record-owner-draw` route** — active endpoint that writes owner pay to `expenses` instead of `owner_capital_entries`, violating ADR-001. Job-linked owner pay recorded through this route will not appear on the Owner Pay dashboard.

5. **Hard-delete on financial records** — expenses and invoices can be permanently destroyed with no recovery path, no audit trail, and no void/correction pattern.
